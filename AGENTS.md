# AGENTS.md

## Project overview

Aurora Engine is an Ethereum Virtual Machine implemented as a NEAR smart contract. This repository is a Rust 2024 workspace with a `wasm32-unknown-unknown` contract build, supporting `no_std` crates, standalone execution/storage tooling, Solidity contracts, and integration tests that run against NEAR sandbox.

Treat consensus-visible behavior, gas accounting, transaction decoding, precompile behavior, contract entry points, storage keys, and serialized data as compatibility-sensitive.

[`ARCHITECTURE.md`](ARCHITECTURE.md) is the source of truth for component boundaries and runtime/data flows. Read the relevant sections before a cross-crate, persistence, promise, connector, or execution change. Update it when a change introduces a component, moves a responsibility, or materially changes a documented flow or invariant.

## Repository map

- `engine/`: core EVM execution, NEAR contract methods, state, accounting, and cross-contract calls. The exported contract API is in `engine/src/lib.rs`.
- `engine-types/`: shared public types, contract parameters, storage keys, and Borsh/Serde formats.
- `engine-sdk/`: abstractions over the NEAR runtime plus host implementations of cryptographic operations.
- `engine-precompiles/`: Ethereum and Aurora-specific precompiles and their gas rules.
- `engine-transactions/`: Ethereum transaction envelopes, decoding, signature recovery, and intrinsic gas.
- `engine-hashchain/`: hashchain and Merkle data structures.
- `engine-modexp/`: memory-conscious modular exponentiation implementation.
- `engine-test-doubles/`: mock IO, promise, and tracing implementations for tests.
- `engine-tests/`: cross-crate tests, NEAR sandbox tests, fixtures, and gas benchmarks.
- `engine-workspace/`: helpers for NEAR workspace integration tests.
- `engine-standalone-storage/` and `engine-standalone-tracing/`: native storage and tracing support.
- `engine-tests-connector/`: ETH connector integration tests.
- `etc/eth-contracts/`: Solidity contracts and committed generated bytecode used by the engine.
- `etc/xcc-router/`: separate NEAR contract with its own Cargo workspace and lockfile.
- `etc/tests/`: standalone fixture contracts; these are intentionally excluded from the root Cargo workspace.
- `Makefile.toml`: canonical build, lint, and test task definitions. Check it before inventing a new command.

## Architectural boundaries

- Keep the functional core independent of its host. Contract methods and execution logic should depend on the `engine-sdk` `IO`, `Env`, and `PromiseHandler` traits, not directly on NEAR host functions. Host calls belong in the runtime adapter in `engine-sdk` unless an existing documented low-level exception applies.
- Keep `engine/src/lib.rs` exports thin: construct the runtime adapter, delegate to `engine/src/contract_methods/`, and convert the returned error through the established contract boundary.
- `Engine` is the `aurora-evm` read/write backend. Use the existing state helpers and `engine-types` key constructors rather than performing ad hoc raw storage access.
- Preserve on-chain/standalone equivalence. Reusable behavior belongs in generic engine or contract-method code, not only in the WASM export or only in standalone code. If an input or execution rule changes, review standalone message decoding and historical replay compatibility.
- Treat `PromiseHandler` as a privileged capability. User-controlled bytes or ordinary EVM logs must never become arbitrary calls from the engine account. Promise-producing precompiles must emit the validated, engine-owned encodings handled by the existing internal-log path.
- Make data formats explicit at every boundary: Ethereum transactions use RLP envelopes, EVM calls use Ethereum ABI, most internal contract parameters/state use Borsh, and NEP-141 interfaces use their required JSON representation. Do not silently change a format.
- The deployed NEAR contract and its storage are authoritative. Standalone storage is a replay/history representation and must reproduce the contract; it must not define divergent execution semantics.

## Toolchain and setup

- Use the Rust toolchain pinned in `rust-toolchain`, including `rustfmt`, `clippy`, and the WASM target.
- Install `cargo-make`; repository workflows use `cargo make ...`.
- Contract builds require the `wasm-opt` version documented in `README.md`. Solidity workflows require Node.js, matching the version in CI, and Yarn. Full integration tests may also require Docker, NEAR sandbox dependencies, and local native libraries.
- Keep `Cargo.lock` and the lockfiles under standalone projects committed. Do not upgrade dependencies or regenerate lockfiles unless the task requires it.

## Working rules

- Make the smallest coherent change. Do not refactor unrelated code or rewrite existing comments while fixing a focused issue.
- Preserve the existing crate boundary. Put reusable parameter and wire types in `engine-types`, runtime abstractions in `engine-sdk`, transaction envelope logic in `engine-transactions`, precompiles in `engine-precompiles`, and test-only implementations in `engine-test-doubles`.
- The contract-facing crates support `no_std`. Do not introduce `std` APIs into `engine`, `engine-types`, `engine-sdk`, `engine-precompiles`, `engine-transactions`, `engine-hashchain`, or `engine-modexp` without an appropriate feature gate. A native test passing is not evidence that the WASM contract still builds.
- Workspace dependencies normally set `default-features = false`; enable only the minimum explicit features needed by a crate.
- Follow the workspace lints in `Cargo.toml`: Clippy `all`, `pedantic`, and `nursery` are denied, and CI also denies warnings and `clippy::as_conversions`. Prefer checked or explicit conversions over `as` casts.
- Format Rust with the workspace formatter. Do not hand-format generated Solidity artifacts.
- Avoid new `unsafe` code. If it is genuinely required for an FFI or cryptographic boundary, keep it minimal, document its safety invariants, and add focused tests. `engine-transactions` forbids unsafe code entirely.
- Use existing error types and established `sdk_unwrap`/`sdk_expect` behavior at contract boundaries. Do not turn malformed external input into a host panic accidentally.
- Add or update tests with behavior changes. Prefer unit tests beside the implementation; use `engine-tests/src/tests/` for cross-crate, contract, or sandbox behavior.

## Compatibility and security invariants

- Do not reorder or change Borsh-serialized fields, enum variants/discriminants, storage prefixes, or raw storage-key construction without an explicit migration and backward-compatibility plan. Extend `EngineState` through a new versioned Borsh representation and conversions from all supported older versions.
- Treat persistent key prefixes as append-only identifiers. Use the established generation mechanism for clearing EVM account storage; do not attempt to enumerate NEAR storage or reuse an old prefix for a new purpose.
- Treat changes to `engine/src/lib.rs` exported functions as public contract API changes. Preserve method names, input encodings, output encodings, authorization checks, payable behavior, and callback assumptions unless the task explicitly changes the API.
- Preserve checked arithmetic and gas accounting. For EVM behavior, compare against the relevant Ethereum hard-fork/EIP rules and test boundary values, malformed input, overflow, out-of-gas, and failure paths.
- Precompile changes must keep address registration, fork activation, required gas, output encoding, pause behavior, and error/refund behavior aligned. Register additions in the correct hard-fork constructor and exercise both normal and `error_refund` feature paths when relevant.
- Transaction changes must cover all affected envelope types and signature/chain-ID edge cases. Keep decoding strict: reject malformed, unsupported, or trailing data according to the established behavior. Review the block-height-aware compatibility parser used by standalone replay whenever parsing rules change.
- NEAR promise and cross-contract-call changes must preserve callback ordering, attached gas/deposit accounting, predecessor/current-account assumptions, and failure handling.
- Changes to state or execution semantics should be checked against both the on-chain engine and standalone replay/storage behavior.

## Generated and versioned artifacts

- `bin/`, `target/`, Solidity `artifacts/`, Solidity `cache/`, and `node_modules/` are generated and must not be committed.
- Files under `etc/eth-contracts/res/` are committed contract artifacts. If the corresponding Solidity changes, regenerate them with `cargo make build-contracts`, review the bytecode diff, and run `scripts/verify_evm_erc20.sh` when `EvmErc20` is affected.
- Do not edit generated `.bin` or `.hex` files manually.
- Do not change root `VERSION` or `etc/xcc-router/src/VERSION` unless the task includes a version/release or router migration change.

## Validation

Start with the smallest relevant check, then expand according to risk. Report which commands were run and any checks that could not run because of missing system dependencies.

Choose tests at the boundary affected by the change:

- Use crate unit tests with in-memory IO for parsing, arithmetic, storage helpers, and isolated precompile behavior.
- Use `engine-tests`/`AuroraRunner` for the compiled WASM ABI, host behavior, gas measurements, and broad EVM behavior.
- Use `StandaloneRunner` or the existing equivalence checks for persistence, historical parsing, and execution/state changes.
- Use `engine-workspace` tests when real NEAR receipts, callbacks, access keys, upgrades, or multiple contracts are involved.
- Use Solidity fixtures for application-level EVM and ABI compatibility.

### Focused Rust changes

```sh
cargo test --profile fast-link -p aurora-engine test_name
cargo make check-fmt
```

Use the normal profile when gas measurements or optimized behavior matter. For feature-sensitive code, also test the relevant feature set explicitly; common contract combinations are `contract` and `contract,error_refund`.

### Workspace and contract changes

```sh
cargo make clippy
cargo make test-workspace
```

`test-workspace` first builds the integration-test WASM and therefore needs `wasm-opt` and the Solidity toolchain. For a production contract build, run:

```sh
cargo make build
```

This must produce `bin/aurora-engine.wasm`. For XCC router changes, run `cargo make build-xcc-router` and the router's relevant tests.

### Solidity changes

```sh
cargo make check-contracts
cargo make test-contracts
```

### Full pre-PR validation

```sh
cargo make check
cargo make test-flow
```

`cargo make check` also runs unused-dependency checking with the nightly version pinned in `Makefile.toml`. `cargo make test` adds the ignored modular-exponentiation benchmark suite and is appropriate when modexp or performance-sensitive execution changes.

## Pull requests and commits

- Target `develop` unless the maintainer or release task says otherwise; `master` is the deployment-ready branch.
- Keep a change focused on one goal. Document user-visible or operational changes and call out compatibility, gas, state-migration, or bytecode-size effects.
- Changes that affect users or protocol behavior may require an Aurora Improvement Proposal discussion before implementation.
- Update `ARCHITECTURE.md` in the same change when component ownership, dependencies, runtime boundaries, persistence, interoperability, or the build/test topology changes.
- In the final handoff, summarize behavior changed, tests run, generated artifacts updated, and remaining risks or unverified expensive checks.
